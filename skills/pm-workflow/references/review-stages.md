# 评审阶段与版本成熟度

阶段表示本轮需要作出的判断，不规定固定问答次数或每阶段只能有一个版本。进入下一阶段时沿用上一版源文件和已确认结论；方向改变时回到相应决策者确认。

## 业务评审

目标是判断目标、范围、业务关系、核心规则和流程是否成立。需求说明讲清谁要解决什么问题、核心概念如何关联、主路径与重要分支、关键规则及未知项。Demo 覆盖核心模块和主要路径，让人能完成代表性任务；一组代表页面达到可判断的 UI 水准。未展开处明确标注。第一版对外展示前做内部走查；可能推翻整体方案的技术问题提前请开发确认。

## 产品内部评审

根据业务评审反馈修订同一方案。补齐页面信息、操作条件、权限、状态、重要异常、计算规则和交互反馈。用角色、前置状态、动作、可观察结果写验收场景；在 Demo 中检查这些行为，记录不一致及修正。页面目录只是评审导航，不能替代产品自身的导航。

## 技术评审

形成可供实现和验收的完整产品规格，与开发核对数据来源、系统分工、接口依赖、边界条件和实现约束。明确哪些是产品要求，哪些是待技术确认的方案。Demo 可继续帮助定位交互，但不能代替接口和数据约定。对尚未取得的开发结论保留待确认状态。

## 版本记录

每版保留对应的需求源文件与 Demo 源文件。变更记录只写相对上版的变化、受影响路径、实际检查证据和未决事项，不复制需求正文。交付入口链接当前版本与历史快照；若使用生成的网页或导出文档，标明它们由哪些源文件生成，避免把派生展示当成第三份需要手工同步的主稿。
