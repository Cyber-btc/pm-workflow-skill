# 产品方案协作

帮助用户尽早通过具体体验检查方案，并让需求意图与 Demo 的实际行为在每次修改后保持一致。沿用用户已经确定的阶段和材料；没有既定阶段时，根据本次评审要决定什么，选用[阶段参考](references/review-stages.md)。不要因为调用本 Skill 就启动发布、业务执行或其他外部操作。

## 开始工作

1. 从已有决定和材料提取目标用户、主要模块的作用、关键规则、争议及本轮要作出的判断。区分已确认事实、工作假设、待决定事项和未展开范围；只在缺失信息会实质改变结果时问一个关键问题。
2. 按用户任务梳理从入口到结果的完整路径，先给出简短的整体关系与本版范围，再制作对应需求和 Demo。需要时用图示解释关系、分支或状态；未展开的分支明确标出。
3. 默认交付一个可打开的 HTML 评审入口：排版展示需求说明，进入对应的可操作 Demo，并能从页面或章节就近查看详细规则、返回体验。产品路径靠自身导航走通；评审目录、批注或模拟控制留在交付层。尊重已有工程和用户指定形式，无需改用特定框架。
4. 指定需求与 Demo 的源文件。HTML 阅读视图由需求源内容生成或呈现，更新源文后刷新展示；不要让评审页成为第三份手工维护的规则正文。每版保留能恢复的需求、Demo、必要资源和简短变更记录，历史快照不得悄悄引用新版内容。

## 让两份源文件一起演进

- 修改从需求说明、Demo 或页面反馈开始都可以。反馈若触及已确认业务规则，先指出冲突及决定权归属；普通可逆实现选择由 Agent 继续完成。找出受影响的路径、角色权限、规则、页面、状态、异常、文案和验收场景，再更新相应源文件与阅读视图。
- 对关键场景逐项对照：角色和前置状态、动作、预期可观察结果、Demo 实际结果及证据。发现不一致时修正或明确列为未解决项；不要用代码存在或格式通过代替交互验证。
- 对不确定的规则写出假设及其影响。可能推翻方案的技术约束应尽早请相应人员确认；不得把 AI 推测的接口、数据来源或实现限制写成已确认事实。
- 产品界面按终端用户任务组织导航、内容和反馈；评审入口按阅读、定位、比较和批注组织。评审说明和模拟控件留在交付层，产品界面保留用户必须知道的条件、费用、错误与后果。

## 交付与验证

内部走查后再交给评审者。从 HTML 入口检查需求阅读、规则定位、返回体验与产品主路径；实际操作 Demo 并观察结果。能使用浏览器时检查渲染、布局和交互，不能使用时直说哪些行为未实测。阶段成熟度与检查重点见[阶段参考](references/review-stages.md)。

交付时给出入口、本版改变及原因、受影响位置、实际检查证据、未覆盖路径和待决事项，让评审者能定位变化而无需重读全文。分别说明文件结构、程序运行、交互行为与使用效果的验证范围；未经测量不声称提效。这里的“联动”是 Agent 的工作要求，不代表已提供浏览器编辑、自动回写或自动语义同步程序。
