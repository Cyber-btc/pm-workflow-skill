# 产品方案协作

帮助用户尽早通过具体体验检查方案，并让需求意图与 Demo 的实际行为在每次修改后保持一致。沿用用户已经确定的阶段和材料；没有既定阶段时，根据本次评审要决定什么，选用[阶段参考](references/review-stages.md)。不要因为调用本 Skill 就启动发布、业务执行或其他外部操作。

## 开始工作

1. 从已有材料提取目标用户、要完成的任务、关键规则、当前争议和本轮评审决定。标出已确认事实、工作假设和待确认事项；只在缺失信息会改变范围、结果或风险时问一个关键问题。
2. 按用户活动、步骤和必要分支梳理完整路径，再确定本版可体验的范围。未实现的分支明确标出，不能让可点击的假动作看起来已完成。
3. 同一评审版本至少提供可读取的需求说明、可操作 Demo，以及简短的变更与检查记录。需求说明记录意图、规则、状态和验收场景；Demo 源码负责实际界面与行为。评审入口可以链接或呈现两者，但不再独立维护一份需求正文。保留每版快照，使评审者能回到当时的需求与 Demo。

## 让两份源文件一起演进

- 修改从需求说明或 Demo 开始都可以。先找受影响的用户路径、规则、页面、状态、异常、文案和验收场景，再更新相应源文件。不要只修改被点名的表面元素。
- 对关键场景逐项对照：角色和前置状态、动作、预期可观察结果、Demo 实际结果及证据。发现不一致时修正或明确列为未解决项；不要用代码存在或格式通过代替交互验证。
- 对不确定的规则写出假设及其影响。可能推翻方案的技术约束应尽早请相应人员确认；不得把 AI 推测的接口、数据来源或实现限制写成已确认事实。
- 产品界面按终端用户任务组织导航、内容和反馈；评审入口按阅读、定位、比较和批注组织。评审说明和模拟控件留在交付层，产品界面保留用户必须知道的条件、费用、错误与后果。

## 交付与验证

内部走查后再交给评审者。检查本轮涉及的主路径和重要分支，实际操作 Demo 并观察结果；能使用浏览器时检查渲染、布局和交互，不能使用时直说哪些行为未实测。阶段成熟度与检查重点见[阶段参考](references/review-stages.md)。

交付时给出版本文件位置、本版改变、已做检查及证据、未覆盖路径和待决事项。分别说明文件结构、程序运行、交互行为与使用效果的验证范围；未经测量不声称提效。这里的“联动”是 Agent 的工作要求，不代表已提供浏览器编辑、自动回写或自动语义同步程序。
